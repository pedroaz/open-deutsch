# Full implementation TODO

Status: canonical execution plan  
Last updated: 2026-08-15

This is one dependency-ordered TODO, not a phase plan. Tags such as `[desktop]` and `[mcp]` identify ownership only. The implementation agent should work from the first unchecked item downward and continue looping while safe, unblocked work remains. The product name is **Open Deutsch**.

The accepted product and architecture decisions remain authoritative. If this checklist conflicts with `decisions.md`, update the checklist to match the decision log before implementing.

## Goal for the implementation agent

Create a Codex goal with this objective when implementation begins:

> Complete every unchecked item in `docs/implementation-plan.md` in dependency order. Implement, verify, mark complete, and continue automatically while safe unblocked work remains. Preserve user changes, use Make as the public workflow, never use the learner's real data in automated tests, and never invoke account-consuming verification without explicit user confirmation. Finish only when every in-scope checkbox is complete and the final acceptance checks pass.

Do not set a token budget unless the user explicitly requests one.

## Agent loop

For every goal turn:

1. Read this file, `docs/decisions.md`, and the current worktree state.
2. Select the first unchecked item whose prerequisites are complete.
3. Implement the smallest coherent change that fully satisfies that item. Do not mark shells, placeholders, skipped tests, or TODO-only code complete.
4. Run the narrowest relevant test first, then the required broader gate described by the item.
5. Fix failures before proceeding. Inspect Playwright traces, screenshots, process logs, and disposable test data rather than retrying blindly.
6. Mark the item `[x]` only after its completion condition is true. Add a short indented note only when an implementation choice or verification command is not obvious from the code.
7. Continue immediately to the next unblocked item; do not stop merely to report progress.
8. If an item is genuinely blocked by external state or a missing user decision, record `Blocked:` beneath it and continue with later items only when they do not depend on it.

After the relevant scripts exist:

- Run targeted tests during editing.
- Run `make test-fast` after domain, persistence, contract, IPC, App Server adapter, or MCP changes. `make test` is only a convenience alias for this same fast gate.
- Run the affected `make test-e2e` journey after Electron main/preload/renderer changes.
- Run deterministic `make test-plugin` after plugin manifest, skill, tool metadata, or MCP workflow changes.
- Never invoke `make verify-live` or `make verify-plugin` through ordinary agent iteration, `make check`, `make test-all`, automated test discovery, or CI.

## Definition of done for every item

An item is complete only when:

- production behavior is implemented, not merely mocked;
- types and public contracts are updated;
- success, empty, invalid-input, and relevant failure paths are handled;
- deterministic tests cover the behavior at the lowest useful layer;
- user-facing changes are accessible by keyboard and meaningful labels;
- user-facing strings are localized through English/German i18n keys and checked for overflow;
- UI changes follow `docs/design-direction.md` and update the component gallery when they add shared states;
- operational changes emit useful redacted human-readable logs where diagnosis requires them;
- no private learner data, tokens, or generated staging content enters Git;
- relevant documentation is updated when behavior or a decision changes.

Validation spikes are complete when the disposable proof, recorded command/evidence, accepted decision or explicit release blocker, and cleanup of throwaway artifacts are complete. They do not need production UI, but they must not leave placeholder behavior that later tasks silently treat as production.

## Interview coverage contract

The checklist is incomplete unless it implements and verifies all of the following accepted directions:

- Open Deutsch naming, `open-deutsch://`, `dev.opendeutsch.app`, clean OD branding, and Linux-only delivery;
- existing compatible Codex prerequisite, managed account reuse/login, runtime model discovery, and no API-key fallback;
- isolated no-network/no-shell/no-unrelated-tool App Server turns for bounded desktop AI;
- an opinionated Git-managed Markdown/YAML A1–B2 curriculum and read-only AppImage snapshot, with no application Git management;
- versioned data-root switching that prevents a stale MCP process from touching the previous dataset;
- deterministic tests separated from explicit usage-consuming `make verify-live` and `make verify-plugin`;
- stable guided plugin marketplace/CLI installation plus Make install/refresh/status/uninstall targets;
- one general History area and complete writing, grammar, goal/topic vocabulary lessons with simple SRS, natural-request custom lessons/exercises, reading, Codex listening/speaking, optional placement, weekly planning from either surface, and four-skill evidence journeys;

- English-default EN/DE UI, separately configurable teaching language, React Aria, CSS Modules/tokens, Lucide, component gallery, and representative visual checks;
- Make-first lifecycle, quality, test, packaging, logging, and integration commands backed by full pnpm scripts and safe tracked processes;
- strict TypeScript, ESLint flat configuration, Prettier, package-boundary and Electron/accessibility rules;

- an Open Deutsch cloud backend or cloud synchronization;
- multi-user/classroom/social features;
- rebuilding live Voice inside the desktop app;
- automatic backups, managed snapshots, or in-app data-folder moving;
- application-level SQLite encryption;
- a general-purpose embedded Codex client;
- bundled Codex, API-key authentication, or a separate billing path;
- public HTTPS MCP hosting or public plugin submission;
- MCP Apps UI without a separately approved interaction that materially benefits from it;
- Windows audits, builds, packaging, or product support;
- local audio generation, import, storage, playback, or Voice automation;
- clipboard/copy-prompt/manual-selection handoff UI;
- automatic AppImage updates or background update checks;
- application Git commands or curriculum synchronization;
- a dedicated crash-loop recovery product, telemetry, or cloud crash reporting;
- formal CEFR certification or exam accreditation.
